# DeepHub 云端协议 · 版本登记簿

协议的两端分居两个仓库：**客户端实现开源**（本包），**服务端不开源**。

---

## 版本登记簿

| 版本 | 新增能力 | 日期 | 含义 |
|---|---|---|---|
| **1** | `base` | 2026-09-17 | `DH-SIGN-V1` 请求签名、`DH-RESP-V1` 响应签名、零知识账号（scrypt + HKDF + AES-256-GCM 信封）、MK 验证子、X25519 身份与端到端投递、好友与加密备注 |

---

## 演进规则

`added` 是一张**只增不减**的表，`capabilitiesFor(v)` 返回 ≤ v 的累积并集。

| 动作 | 做法 |
|---|---|
| **加一个能力** | 版本号 +1，在 `added` 中增加一行 |
| **下线一个旧行为** | **抬 `MIN_SUPPORTED`**，且必须先走弃用窗口。**不要从 `added` 中删除条目** |
| **改一个行为** | 加一个新能力（版本 +1），日后再抬 `MIN_SUPPORTED` 关闭旧路径 |

---

## 发版顺序

| 动作 | 谁先上线 | 原因 |
|---|---|---|
| **加一个版本**（v2 出现） | **服务端先** | 服务端未认识 v2 时，客户端声明 v2 无意义：客户端按 v2 的能力行事，服务端仍按 v1 应答 |
| **抬 `MIN_SUPPORTED`** | **客户端先** | 否则尚未升级的客户端会被直接拦在门外 |

### 窗口期客户端须支持两个版本

「服务端支持 v2」到「客户端全部升至 v2」之间存在窗口期，其间两种客户端并存。
因此**新客户端必须同时具备 v1 与 v2 的能力**，由 `negotiate()` 取双方 `current` 的较小者决定本次使用的版本。

以响应签名为例：新客户端需**同时支持验证 `DH-RESP-V1` 与 `DH-RESP-V2`**，按协商结果选用。

---

## 抬 `MIN_SUPPORTED` 的判据

判据不是「设备表中所有行都 ≥ N」：版本号由客户端启动时上报，长期离线的设备不会上报。

判据是**最近 N 天活跃过的设备均 ≥ 目标版本**。其余设备恢复联网后会收到 426 `client_too_old`
及对应的升级提示。

抬下限只改服务端一个常量，可随时回退。

## 协商流程

```
启动时（一次）—— 接入位置见下方「上报的接入点」
  未登录 →  GET  /api/v1/protocol              仅获取区间
  已登录 →  POST /api/v1/protocol { proto: N }  记录 N 至设备行，同时获取区间

服务端应答（签名覆盖，弃用提示包含在内）
  { current, min_supported, deprecated_below, sunset, capabilities }

之后每个请求
  服务端在**验签通过之后**比对设备行的版本；低于下限 → 426 client_too_old
```

三点：

1. **版本号由启动探测上报，不依赖登录。** 设备密钥跨升级、跨登出均保留，免密启动不走登录流程；
   挂在登录上会使设备版本号停留在最后一次输入密码的时间。
2. **广播必须走验签通道。** `/api/health` 不验签，将版本区间置于其上等同于开放降级通道：
   中间人可谎报服务端支持的范围。
3. **426 守卫有且只有两条豁免。**
   - `/api/v1/protocol`（GET 与 POST）：否则过旧的客户端无法获知被拦截的原因。
   - `POST /api/v1/account/register`：该路由不建账号、不建设备行，仅落一条 pending 记录并发送验证码邮件；
     真正的校验在下一步的 `verify-email`，那一步携带 `proto` 且确实受拦截。不豁免的后果是：
     客户端的 register 请求体中**从不包含 `proto`**（`account.ts` 的 `deviceMeta()` 仅提供
     pubkey / name / platform），`minSupportedClient` 一经抬升，**所有版本**的客户端都无法注册新账号。

### 上报的接入点

上报必须接在每次启动都会执行的位置：

| 消费方 | 接入位置 |
|---|---|
| DeepHub 桌面端 | `CloudService.attachSync()` 的免密分支，与 `engine.start()` 并列 |
| dsh 插件 | `src/index.ts` 的启动预热（`if (st.loggedIn) void svc.probe()`） |

**不要只挂在 `probe()` 上**：桌面端的 `probe()` 仅由账号面板与朋友页触发，从不打开这两处的用户将永不上报版本。
**也不要只挂在登录上**：设备密钥跨升级、跨登出均保留，「已升级但未重新登录」是常态。

### 客户端不自我封锁

客户端在本地判出 `client_too_old` 后**照常发送请求**，由服务端回 426。裁决权只在服务端，
客户端仅负责向用户说明。代价是一次注定失败的往返，收益是本地判断不会锁死一个实际可用的客户端
（离线、时钟偏差、探测被中间人阻断均属此类）。

探测结果无法解析时落 `unknown`。**`unknown` 不是错误**，离线是常态。

### 解析必须严格

`open` 路由不消耗 nonce，中间人可将客户端的 nonce 转发至另一个 `open` 路由（如 `/account/kdf`），
取回一个**签名合法**的 200 再作为协议应答返回。因此：

- 字段缺失、类型不符、`min > current`、`current` 非非负整数 —— **一律落 `unknown`，不得落 `ok`**
- **客户端不得因协商结果降低自身的 `CLIENT_MIN_SERVER`**

## 修改本包之前

协议的另一半位于一台不公开的服务器上，**单独修改本包会造成故障**：

- 改动请求签名的字段顺序 → 全网请求立即 401，且服务端刻意不区分失败原因
- 改动信封字段 → 对象上传返回 400，错误信息仅为 `bad_envelope:<字段>`
- 改动 HKDF info 串 → 已有数据无法解密

因此协议部分**不接受外部 PR**。插件部分（`packages/dsh-deephub-share`）接受 PR。

发现安全问题请按 [SECURITY.md](../../SECURITY.md) 报告。
